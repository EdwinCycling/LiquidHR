# CORE-DB-25P02-01 — Core TEST transaction failures

Date: 2026-10-18 (UTC)

Scope: Core TEST and the shared STAR Performers / Payroll request paths. Payroll Lab TEST remains a separate database.

The initial read-only 24-hour review counted 27 Core TEST `25P02` responses and none in Payroll Lab TEST. The observed repeated SQL timeouts at 08:30 UTC include `GET /talent_capabilities`, `/talent_levels`, and `/job_profile_capability_requirements`.

## Root cause and request path

The direct failing SQL is the PostgREST-generated `SELECT` for the requested capability/level catalog rows. It is not an RPC. The shared caller is `readRecordRows()` in `apps/hr-suite/lib/talent/employee-capability-service.ts`, which launched capability, level, and employee lookups together with `Promise.all`.

The STAR Performers V2 manager-detail flow calls `listTalentEmployeeCapabilityRecords()` through its optional read path (`lib/star-performers/v2-service.ts` in the protected STAR V2 worktree). This is the product flow matching the catalog IDs and projections in the logs. Payroll Lab itself had no matching database errors. Payroll requests authenticate and read shared Core data through `lib/payroll/source/liquid-hr-source-provider.ts` and the same Core `requirePermission()` context, so a poisoned Core PostgREST backend could also break a Payroll page even though the Payroll Lab database is clean.

The `57014` timeout came from nested manager-read RLS checks. The manager branch in `20260803082559_optimize_talent_capability_rls_short_circuit.sql` joins capability requirements, profile versions, job profiles, and employee organizations. Those tables have their own manager-read policies, which repeat similar `EXISTS` joins and invoke organization visibility checks (`can_manage_employee`, `current_user_has_hr_group_permission`, and preboarding checks). The read-only authenticated `EXPLAIN` expanded the capability request to 707 subplans. The supporting manager/profile indexes already exist, so this is not an absent-index failure.

PostgREST 14.5 owns each REST request transaction and the connection pool; the application uses Supabase HTTP queries and has no transaction handle on which it can issue `ROLLBACK`. PostgREST documents request transaction rollback on database errors ([transaction handling](https://docs.postgrest.org/en/stable/references/transactions.html)). The available logs prove that the same backend later received statements while in an aborted transaction, but do not expose the pooler's transaction-boundary commands, so they do not establish whether the failed request's rollback was skipped or a later request entered an already-aborted transaction. The app fix removes the observed timeout trigger and stops the shared capability-read flow from starting later catalog/employee requests after an earlier read fails. If `25P02` persists after the RLS query fix is applied, investigate the PostgREST/Supavisor transaction reset path using backend logs; the application must not issue an unrelated rollback request or add a retry loop.

## Changes

- `20261018083400_core_db_25p02_manager_scope_optimization.sql` adds one fixed-search-path `SECURITY DEFINER` predicate that retains the existing manager permission, active-version dates, current direct-manager assignment, and all four `employee_organizations` read-visibility paths. It replaces only the manager-read branches of five SELECT policies. Existing `talent:read`, `talent:manage`, and self-read branches remain. No role permissions, grants on data tables, RLS enablement, write policies, or payroll data are changed.
- `employee-capability-service.ts` reads capabilities, levels, and employees in order and stops at the first error; it logs only a fixed operation label and validated SQLSTATE, then returns the existing safe service error.
- Shared Core auth/context database failures now log only the operation and SQLSTATE and throw a generic server error without retaining the PostgreSQL error object.
- `app/error.tsx` renders localized, actionable feedback without displaying or logging the raw Next/PostgreSQL error.
