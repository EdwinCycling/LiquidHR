## OAuth consent authorization-binding fix

The hosted ChatGPT authorization row is `pending` with `user_id = NULL` before consent; that is expected in Supabase's flow and is no longer treated as an account mismatch. The consent page accepts only the `authorization_id` from the request, calls Supabase `getAuthorizationDetails`, requires the returned authorization ID to match exactly, and takes client name, callback URI, scopes and resource from that response. Supabase's response shape distinguishes a pending consent request (authorization details) from an already-resolved request (`redirect_url`); errors, mismatched IDs and resolved requests fail closed. See [Supabase `getAuthorizationDetails`](https://supabase.com/docs/reference/javascript/oauth-server-getauthorizationdetails) and [OAuth 2.1 server flow](https://supabase.com/docs/guides/auth/oauth-server/getting-started).

If there is no valid LiquidHR session, the route preserves the exact opaque ID in `/login?next=/oauth/consent?authorization_id=...`. On return, details are fetched again. Approve and deny actions revalidate the session, pending response, Employee-only context, scopes and Supabase callback URL, then call only `approveAuthorization` or `denyAuthorization`; no direct authorization-table write or service-role approval is used. The small service-role RPC only registers the DCR client after Supabase has approved authorization. The callback redirect URI is never taken from request/form data.
